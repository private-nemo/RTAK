# RTAK Inlet — Reticulum over Internet

Extends the RTAK mesh across the internet while maintaining the full Reticulum encryption stack. CoT traffic routed through the inlet is indistinguishable from ordinary HTTPS traffic to any deep packet inspection, firewall, or middlebox.

---

## Why This Works

Reticulum's TCP interface already solves the core problem. When two Reticulum nodes connect over TCP, the entire transport is binary-encoded Curve25519+AES frames. There is no protocol signature identifying it as Reticulum, no CoT XML visible, nothing that looks like tactical data. To a passive observer it looks like an encrypted binary protocol.

The RTAK Inlet adds a second layer by wrapping the Reticulum TCP connection in real TLS via `stunnel`. The result:

```
CoT XML
  └─ LXMF message (Reticulum LXMF)
       └─ Reticulum frame (Curve25519 key exchange, AES payload)
            └─ TCP stream
                 └─ TLS (stunnel, RTAK CA cert)
                      └─ Internet (port 443 or any port)
```

Port 443 + TLS handshake = looks exactly like HTTPS to any network observer. The inner Reticulum encryption means even if the TLS layer were stripped, the payload remains encrypted. There are two independent encryption layers with no shared keys.

---

## Two Modes

### Basic Mode — Raw TCP (port 4242)

Adds a `TCPServerInterface` to the OmniNode's Reticulum config. Traffic is Reticulum-encrypted binary on a configurable port. Fast to set up, visible as a non-standard binary protocol on inspection.

### Stealth Mode — TLS on port 443

Adds stunnel in front of the TCP interface. Traffic arrives on port 443, undergoes a real TLS handshake (using the RTAK server cert already generated by `setup_pi.sh`), and is forwarded to Reticulum's TCP listener on localhost. Indistinguishable from HTTPS at the network layer.

The stealth mode uses the same TLS certificates generated during `setup_pi.sh`. No additional PKI setup required.

## OmniNode Setup

Run `setup_inlet.sh` on the OmniNode Pi after `setup_pi.sh` has already been run:

```bash
sudo bash rtak_inlet/setup_inlet.sh
# or with custom port:
sudo bash rtak_inlet/setup_inlet.sh --port 4242
# for stealth mode (TLS on 443):
sudo bash rtak_inlet/setup_inlet.sh --stealth
```

What the script does:
1. Appends a `TCPServerInterface` block to `/etc/reticulum/config`
2. In stealth mode: installs `stunnel`, writes `/etc/stunnel/rtak-inlet.conf`, enables and starts `stunnel4`
3. Opens the inlet port in UFW
4. Restarts `rnsd` to activate the new interface
5. Prints a connection string for remote operators

## Remote Node Setup

On any remote Reticulum node (another OmniNode, a relay, a laptop running RNS) that should connect to this inlet:

Add this block to `/etc/reticulum/config` (or `~/.reticulum/config`):

```ini
# RTAK Inlet connection — reaches the OmniNode over internet
[interface:rtak_inlet]
  type            = TCPClientInterface
  interface_enabled = True
  target_host     = <omninode-public-ip-or-domain>
  target_port     = 4242   # use 443 in stealth mode
```

Then restart Reticulum: `sudo systemctl restart rnsd`

The remote node's full Reticulum mesh (LoRa links, other TCP peers) becomes reachable through the inlet. Multi-hop routing is automatic.

## Network Requirements

### On the OmniNode's router/firewall:

| Mode | Port | Protocol | Action |
|---|---|---|---|
| Basic | 4242 | TCP | Forward to OmniNode LAN IP |
| Stealth | 443 | TCP | Forward to OmniNode LAN IP |

If the OmniNode has a direct public IP (cellular uplink, VPS bridge, satellite), no port forwarding is needed — just open the port in UFW (the script does this).

### No static IP?

Use a dynamic DNS service. The OmniNode can run `ddclient` pointing to a free DDNS provider (DuckDNS, afraid.org). Remote nodes use the hostname instead of IP:

```ini
target_host = your-node.duckdns.org
target_port = 443
```

## Security Properties

| Property | Status |
|---|---|
| CoT content encrypted | Yes — Reticulum Curve25519+AES |
| Metadata (who is talking to whom) | Partially — stunnel TLS hides CoT protocol; IP addresses still visible to ISP |
| Traffic looks like CoT | No — binary Reticulum frames; TLS in stealth mode adds HTTPS appearance |
| LXMF store-and-forward | Yes — messages queue during link outage, deliver when link restores |
| Peer authentication | Yes — only hashes in `rtak_peers.txt` can inject CoT |
| TLS certificate validation | Yes — uses RTAK CA; remote nodes can optionally validate the cert |

**What this does NOT hide:** The IP addresses of both endpoints are visible to the ISP and any network observer on the path. This protects *content* and *protocol identity*, not *endpoint identity*. For full endpoint anonymization, route through I2P (see below).

---

## Optional: I2P Transport (Maximum Anonymity)

Reticulum has native I2P interface support. Routing through I2P hides both endpoint IP addresses at the cost of higher latency and lower bandwidth — usable for CoT updates but slower than direct TCP.

To add I2P support, install `i2pd` on both nodes and add to Reticulum config:

```ini
[interface:rtak_i2p]
  type            = I2PInterface
  interface_enabled = True
  peers           = <remote-i2p-b32-address>.b32.i2p
```

I2P setup is not covered by `setup_inlet.sh` but is documented in the [Reticulum manual](https://reticulum.network/manual/interfaces.html#i2p-interface).

## Example: Multi-Hop Topology

```
[Field Alpha]                    [Internet]                 [Field Bravo]
  OmniNode-A                                                  OmniNode-B
  LoRa mesh ←→ Bridge ←→ TCP/TLS inlet ←→ internet ←→ TCP/TLS inlet ←→ Bridge ←→ LoRa mesh
    ↕                                                              ↕
  ATAK clients (LAN)                                          ATAK clients (LAN)
```

Both LoRa meshes are bridged through the internet link. Operators on Field Alpha and Field Bravo share SA in real time. An LXMF message fragmented across 10 LoRa packets on one side arrives as one reassembled CoT event on the other. Latency is LoRa propagation + internet RTT.
